# Mods turn any terminal into crosstalk's workspace

crosstalk can get within reach of herdr, Paradev and Conductor without an app. The lever that makes this work is not escape codes. It is **Claude Code mods**, an in-process plugin API that has shipped on by default since v2.1.287. Mods let a plugin draw a pane, a band above the prompt, toasts and its own status line. They also let it intercept deliveries from other sessions so that **"nothing is queued, shown or read by the model"** ([Mods overview](https://code.claude.com/docs/en/plugins/mods/overview)). That fixes the hardest part of the current design, keeping other threads' questions out of the current agent's context, from inside the ordinary session the user already opened, in any terminal. Terminal chrome (titles, tab colours, badges, progress, notifications) is a second, best-effort layer, and it is uneven. Claude Code allows hooks only a narrow allowlist of escape sequences (titles, notifications, progress, BEL). It rejects tab colour, OSC 8 and OSC 1337. It also keeps rewriting the tab title itself, so colour and badges have to come from the crosstalk daemon, through each terminal's API or a write to the session's tty. kitty and WezTerm can be fully driven from outside. Ghostty 1.4 on macOS and iTerm2 are nearly there. Terminal.app and Windows Terminal can only open tabs. tmux is the most programmable of all, but it silently drops plain OSC 9/777/99 notifications and does not answer the OSC 7501 status query. The research confirms the "nothing to start" design: the user's own sessions in their own terminal, and a hidden tmux server only for sessions crosstalk starts. It changes four things. The statusline and question surfaces should move to a mod. OSC 7501 is not herdr's and has almost no readers. Titles should be set through Claude Code's `sessionTitle` rather than fought over. And a click on a notification can reliably focus a tab only if the daemon posts the notification itself.

## Claude Code's own UI is the deepest and safest layer

Classic settings hooks can show the user something, but only as a by-product of an event. Mods give crosstalk a real, persistent UI that the model never sees. A plugin adds `{"modules": ["./register.tsx"]}` to `hooks/hooks.json` and exports `register(on)`. From there it can open a **Pane** (a sidebar in fullscreen mode, inline otherwise) or an **AbovePrompt band** built from Box, Text, Button, Input, Select, Markdown, Link (OSC 8) and Image elements. It can raise toasts, pin a status line, write dim transcript notices, ask questions in the native AskUserQuestion dialog, and register `/commands` that run "at once, with no Claude turn, even while Claude is working" ([Mods overview](https://code.claude.com/docs/en/plugins/mods/overview)). The engine's type declarations for Claude Code 2.1.316 (`plugin-authoring/types/claude-code.d.ts`, marked "EARLY ACCESS") give the exact contract. `$.ui.status(text)` pins one line per plugin under the prompt, up to 2,000 characters. `$.ui.toast(text,{timeoutMs})` "leaves the transcript and the model untouched" (default 4 s). `$.ui.log(text)` is "dim; not sent to the model". `$.clock.every` drives updates on a timer. And **`session.receive` fires "before it is queued: a relay's event, a peer's message, a Remote Control prompt… return `{ consumed: reason }` to take it"**. Mods draw in the terminal, the Desktop Code tab and VS Code. They draw nothing under `-p`, the SDK, cloud sessions or background sessions. `--safe-mode` and `disableAllHooks` turn them off, and admins can restrict them with `allowManagedModsOnly` ([Mods overview](https://code.claude.com/docs/en/plugins/mods/overview)). A pane shows unasked only from 144 columns, or from 110 once the user opens it. Redraws are capped at ten a second, or thirty in the terminal for a shown pane.

This matters for crosstalk because the old surfaces leak into the model in ways that are easy to miss. The hooks reference sets the rules. A synchronous hook's `systemMessage` is shown to the user. Async hooks flip it: "Claude Code delivers the `additionalContext` and `systemMessage` fields… to Claude on the next conversation turn… neither field is shown to you." Several events (Notification, SessionEnd, PreCompact and others) simply discard `systemMessage` ([Hooks reference](https://code.claude.com/docs/en/hooks)). The table below sorts every surface by audience. It is the checklist for the rule that "a question never enters another thread's context".

| Surface | User sees | Model sees | Fit for cross-thread questions |
|---|---|---|---|
| `statusLine` command (multi-line, ANSI, OSC 8) | yes | no | yes, but **a plugin cannot install it**; only `agent` and `subagentStatusLine` survive in plugin settings ([Plugins reference](https://code.claude.com/docs/en/plugins-reference)) |
| Mod `$.ui.status`, toast, `$.ui.log`, pane, band | yes | no | **best** |
| Mod `session.receive` → `{consumed}` | whatever the mod draws | no | **best**, for deliveries over the inbox socket or relay |
| Mod `$.session.append` `type:"system"` / `type:"user"` | notice / hidden row | no / **yes** | `user` only on purpose |
| Mod `command.run` reply `{text, context}` | text row | **yes, both** | return little or no text; draw elsewhere |
| Sync `systemMessage` | yes (some events discard it) | no | only when a hook happens to fire |
| `additionalContext`, async `systemMessage`, SessionStart stdout | no | **yes** | never |
| UserPromptSubmit `decision:"block"` + `reason` | reason shown | no | yes, but the prompt text lands in the transcript file and history ([Hooks reference](https://code.claude.com/docs/en/hooks)) |
| MessageDisplay `displayContent` | replacement text | original text | display-only rewrite |
| `stopReason` / Stop block `reason` | yes | **yes** if the turn continues | never |
| Channels `notifications/claude/channel` | `← source: …` summary | **yes, full tag** | never ([Channels reference](https://code.claude.com/docs/en/channels-reference)) |
| Channel permission relay verdict | no | "never reaches Claude" | yes, for answering another session's permission prompt |
| Skill `` !`cmd` `` output | unclear | **yes** | never ([Skills](https://code.claude.com/docs/en/skills)) |
| Hook `terminalSequence` | terminal chrome | no | yes, for titles and notifications |

Two consequences follow for the design. First, **the design's "hook message" cannot reach an idle session**. A synchronous `systemMessage` appears only when some hook fires, and a user sitting idle in the firmware session fires none. Only `CwdChanged` and `FileChanged` render it "as a brief terminal notification" ([Hooks reference](https://code.claude.com/docs/en/hooks)). A mod timer polling the daemon and raising a band or toast is the first mechanism that can push a question onto the screen the user is looking at, with no model involvement. Second, the statusline the design puts "in every session" cannot ship from the plugin. The mod status line replaces it, and it updates on demand without the 300 ms debounce and per-run shell process of the classic `statusLine`. That command is debounced, cancelled when a newer run starts, and re-run only every `refreshInterval` seconds (minimum 1) when idle ([Statusline docs](https://code.claude.com/docs/en/statusline)).

Answering questions also gets cleaner. The design's `@auth y` routed by a UserPromptSubmit block works, and the `reason` "is not added to context". But by default the block message ends with "`Original prompt:`" followed by the text, written to the on-disk transcript. `suppressOriginalPrompt` hides it only from the on-screen message ([Hooks reference](https://code.claude.com/docs/en/hooks)). A band with Buttons and an Input, or `$.ui.ask`, answers without typing into the prompt at all. Per the 2.1.316 reference, a mod `prompt.submit` hook can also `{drop}` a typed `@auth …` before any turn. Keep the UserPromptSubmit block as the fallback for when mods are disabled. One gap needs a test: whether `$.ui.ask` answers are recorded in model context, since it is implemented as an AskUserQuestion tool call through the hook chain.

Two adjacent surfaces suit sessions crosstalk itself starts better than the user's own. Channels can opt in to **permission relay**. The server receives `permission_request` notifications (a five-letter `request_id`, `tool_name`, `input_preview`) and answers `allow`/`deny`, and "you can answer in the terminal or on your phone, and Claude Code applies whichever answer arrives first" ([Channels reference](https://code.claude.com/docs/en/channels-reference)). Channels still need `--dangerously-load-development-channels`, a flag the user would have to remember. That violates "nothing to start" for their own sessions, but crosstalk controls the command line of sessions it launches. Headless `claude -p --output-format stream-json` with `--permission-prompt-tool` likewise lets the daemon catch every permission question of a background run ([Headless](https://code.claude.com/docs/en/headless)).

## Claude Code guards the title and refuses the tab colour

Look and feel splits along one line: what Claude Code will emit for a hook, and what only the daemon can do. Hooks cannot write to `/dev/tty`, because they "run without a controlling terminal". Instead they return a `terminalSequence`, which Claude Code emits "inside tmux and GNU screen" too. The allowlist is OSC 0/1/2 (titles), OSC 9 including `9;4` progress, OSC 99 (kitty), OSC 777 (Ghostty, urxvt, Warp) and bare BEL. **"CSI cursor and color sequences, OSC palette sequences, OSC 8 hyperlinks, OSC 52 clipboard writes, and OSC 1337"** are rejected, and the sequence applies only in an interactive session with its interface on screen ([Hooks reference](https://code.claude.com/docs/en/hooks)). No mod method sets a title or tab colour either.

The title is contested ground. Claude Code sets it continuously from conversation context. Users report that `CLAUDE_CODE_DISABLE_TERMINAL_TITLE=1` stopped only startup and shutdown writes while ongoing OSC 0 updates overwrote `/rename` titles ([claudeissues #47397](https://claudeissues.com/issue/47397-claude-code-disable-terminal-title-1-doesnt-suppress-ongoing-title-updates-renam)), and Ghostty users wrote shell hooks to win the race ([dev.to](https://dev.to/liran_baba/why-every-ghostty-tab-said-claude-code-and-the-30-line-zsh-hook-that-fixed-it-19h5)). The variable is also too blunt. It "skips the background small/fast-model request that generates a session title, and turns off status reports to your terminal" ([Env vars](https://code.claude.com/docs/en/env-vars)), which kills OSC 7501 along with it. The cooperative path is the `sessionTitle` field, which SessionStart and UserPromptSubmit hooks may return with the "same effect as `/rename`" ([Hooks reference](https://code.claude.com/docs/en/hooks)). crosstalk should name the session after its threads (`auth · tokens`) and let Claude Code paint it. Whether Claude Code composes its OSC title from that name is the first spike to run. Inside tmux the conflict disappears, because Claude Code's OSC 2 becomes the *pane* title while `rename-window`, `allow-rename off` and `set-titles-string` decide what the tab shows ([tmux.1](https://github.com/tmux/tmux/blob/master/tmux.1)).

Everything beyond the title belongs to the daemon. Each terminal family has its own vocabulary, and the cheapest route is a write of one complete sequence, in a single `write()` call, to the session's tty. That tty is found from the pid in `~/.claude/sessions/<pid>.json`. Under Unix pty semantics, bytes written to the slave reach the emulator as output, but they can split one of Claude Code's own redraws mid-frame. ConPTY on Windows has no tty file at all. The daemon must never send a *query* this way, because the terminal's reply arrives on the session's input, inside Claude Code's prompt. That rules out the OSC 7501 handshake from outside. (This is an inference from pty semantics, not a documented behaviour.) The concrete vocabulary, from [iTerm2 escape codes](https://iterm2.com/documentation-escape-codes.html), [kitty remote control](https://sw.kovidgoyal.net/kitty/remote-control/), [kitty notifications](https://sw.kovidgoyal.net/kitty/desktop-notifications/), [WezTerm escape sequences](https://wezterm.org/escape-sequences.html), [wezterm cli](https://wezterm.org/cli/cli/index.html), [Ghostty AppleScript](https://ghostty.org/docs/features/applescript), [WT arguments](https://learn.microsoft.com/en-us/windows/terminal/command-line-arguments) and the [Program Status spec](https://superlogical.com/rex/docs/build/program-status):

```sh
# Any hook (allowlisted, emitted by Claude Code):
{"terminalSequence":"\u001b]2;auth · tokens\u0007"}          # title
{"terminalSequence":"\u001b]9;4;3\u001b\\"}                  # OSC 9;4 progress (state;percent), stop with ESC]9;4 ST
{"terminalSequence":"\u001b]99;i=q1:a=focus;auth needs you\u001b\\"}   # kitty notification, click focuses
{"terminalSequence":"\u001b]777;notify;auth;keep v1?\u001b\\"}         # Ghostty / WezTerm / WT(opt-in)

# Daemon only (rejected by Claude Code):
printf '\e]6;1;bg;red;brightness;211\a\e]6;1;bg;green;brightness;54\a\e]6;1;bg;blue;brightness;130\a' > $TTY  # iTerm2 tab colour
printf '\e]6;1;bg;*;default\a' > $TTY                                   # iTerm2 reset
printf '\e]1337;SetUserVar=crosstalk=%s\a' "$(printf waiting|base64)" > $TTY   # iTerm2 (and WezTerm) user var
printf '\e]1337;SetBadgeFormat=%s\a' "$(printf '\\(user.crosstalk)'|base64)" > $TTY  # iTerm2 badge
printf '\e]7501;state=blocked:kind=question:app=crosstalk:id=auth:msg=%s\e\\' "$(printf 'keep v1?'|base64)" > $TTY
kitten @ --to unix:/tmp/kitty set-tab-color --match var:crosstalk=auth ...    # kitty colour (needs listen_on)
kitten @ --to unix:/tmp/kitty set-tab-title --match var:crosstalk=auth "auth"
wezterm cli set-tab-title --pane-id "$WEZTERM_PANE" "auth"
osascript -e 'tell application "Ghostty" to set name override of selected tab of front window to "auth"'  # 1.4
wt -w crosstalk nt -d ~/wt/auth --title auth --tabColor "#d33682" --suppressApplicationTitle claude
```

The iTerm2 badge syntax and WezTerm's honouring of `SetUserVar` come from training knowledge, not this session's fetches. So does the claim that WezTerm renders tab colour only from a Lua `format-tab-title` handler; what is confirmed is that WezTerm ignores OSC 6 ([WezTerm escape sequences](https://wezterm.org/escape-sequences.html)). Ghostty 1.4 offers no tab colour, only a title override, while 1.3.1 added `progress-style` for OSC 9;4 bars ([Ghostty 1.4.0 notes](https://ghostty.org/docs/install/release-notes/1-4-0); [Ghostty 1.3.0 notes](https://ghostty.org/docs/install/release-notes/1-3-0)). Windows Terminal sets tab colour only at launch.

Themes and images are mostly out of crosstalk's reach and unneeded. A plugin may ship an experimental theme (`themes/`). Its tokens include `composerSidebarBackground`, the background of "a mod's pane", but "Claude Code does not control the terminal's own color scheme" ([Terminal config](https://code.claude.com/docs/en/terminal-config)). Mod Image elements use the kitty or iTerm2 graphics protocols, which is enough for an evidence screenshot inside a pane.

**OSC 7501 is a weaker bet than the design assumes.** It is Superlogical/Rex's Program Status Protocol, attributed to Mitchell Hashimoto ([mitchellh.com](https://mitchellh.com/writing/program-status-osc7501)). It is not herdr's. Claude Code emits it from 2.1.295, with `blocked` plus `permission|question|auth` reasons, but only after a terminal answers `OSC 7501;?`. Once answered, Claude Code also drops the status glyph from its title ([Terminal config](https://code.claude.com/docs/en/terminal-config); [herdr #5073](https://github.com/herdrdev/herdr/discussions/5073)). Ghostty 1.4 parses it but "the Ghostty GUI ignores it for now" ([Ghostty 1.4.0 notes](https://ghostty.org/docs/install/release-notes/1-4-0)). herdr's TUI 0.9.3 handles only OSC 0/2/9 and dropped a raw 7501 record ([herdr #5073](https://github.com/herdrdev/herdr/discussions/5073)), and tmux's OSC dispatcher logs 7501 as unknown ([input.c](https://github.com/tmux/tmux/blob/master/input.c)). Only Rex, TUIOS and a few Ghostty forks consume it ([TUIOS wiki](https://github.com/Gaurav-Gosain/tuios/wiki/Program-Status)). Emitting thread-level records (`id=crosstalk/auth`) costs almost nothing, but status should come from Claude Code hooks, which work in every terminal.

## Interaction lives in mod widgets, tmux primitives and terminal focus APIs

Interaction comes from three places. Inside a session, mods give Buttons that can bind to a keybinding action and a `hotkey`, plus Inputs, Selects, OSC 8 Links, `$.ui.ask`, model-free `/commands`, and `$.ui.view({agentId})`, which switches the main view to an agent's transcript on a person-initiated action (Claude Code 2.1.316 `reference.md`). A plugin cannot ship keybindings: the manifest has no `keybindings` component, and `~/.claude/keybindings.json` is the user's file ([Terminal config](https://code.claude.com/docs/en/terminal-config); [Plugins reference](https://code.claude.com/docs/en/plugins-reference)). So keyboard reach comes from mod hotkeys and commands. The classic statusline supports OSC 8 links in iTerm2, kitty and WezTerm ([Statusline docs](https://code.claude.com/docs/en/statusline)). A `crosstalk://` or `file://` link there is the cheapest clickable element.

tmux, when the user lives in it, has every primitive a switcher needs, and the daemon can install them at runtime with `tmux set`/`bind` rather than by editing `tmux.conf`. The working pattern is the one workmux uses. Hooks set a window user option, and the user's status format renders it through conditionals with no polling ([workmux](https://workmux.dev/guide/status-tracking/)). Clickable ranges, filtered pickers and popups sit on top ([tmux.1](https://github.com/tmux/tmux/blob/master/tmux.1); [CHANGES](https://github.com/tmux/tmux/blob/master/CHANGES)):

```sh
tmux set -w -t @7 @crosstalk_state waiting; tmux refresh-client -S
# extend, don't replace, the user's status (E: double-expands the saved format)
tmux set -gF @ct_old '#{status-format[1]}'
tmux set -g status 2
tmux set -g status-format[1] '#{E:@ct_old}#[align=right]#{W:#{?#{==:#{@crosstalk_state},waiting},#[range=window|#{window_index}]#[fg=magenta]? #W#[norange] ,}}'
tmux bind -n MouseDown1Status if -F '#{==:#{mouse_status_range},ctnew}' 'run-shell "crosstalk new"' 'switch-client -t ='
tmux choose-tree -w -f '#{==:#{@crosstalk_state},waiting}'           # picker of waiting agents
tmux display-popup -E -w 90% -h 90% -T ' auth ' 'tmux -L crosstalk attach -t auth'
tmux new-pane -O -C -D 'crosstalk picker'                               # 3.8 modal floating pane
tmux set-hook -g session-window-changed 'run -b "crosstalk seen #{window_id}"'   # clear "done" on focus
printf '\ePtmux;\e\e]9;auth needs you\a\e\\'                              # notification via passthrough
```

Status ranges of type `user` need 3.4. Floating and modal panes, monitor hooks (`set-hook -B`), `link=` styles (clickable OSC 8 text in the status line) and the `A/` spinner animation need 3.8. A vertical `side-status` sidebar exists only on master ([tmux.1](https://github.com/tmux/tmux/blob/master/tmux.1)). Repology shows Homebrew, Arch and MacPorts on 3.8, but Ubuntu 24.04 on 3.4 and Debian 13 on 3.5a ([Repology](https://repology.org/project/tmux/versions)), so feature detection with `#{version}` is mandatory. For events, a control client avoids polling. Locally, `tmux -C attach -f no-output,ignore-size` with a quoted `refresh-client -B 'st:@*:#{window_name}=#{@agent_state}'` produced `%subscription-changed` within about a second, on tmux 3.4.

Outside tmux, interaction means **focusing the right tab**, and click-to-focus is where terminals differ most. kitty's OSC 99 focuses the originating window on click by default ([kitty notifications](https://sw.kovidgoyal.net/kitty/desktop-notifications/)). Ghostty on GTK focuses the sender ([Ghostty 1.4.0 notes](https://ghostty.org/docs/install/release-notes/1-4-0)), and Windows Terminal's OSC 777 summons the sending window ([WT PR #14425](https://github.com/microsoft/terminal/pull/14425)). Everything else is unconfirmed. The design's promise ("clicking it jumps to that session's tab") therefore holds only if **the daemon posts its own OS notification** and, on click, calls the adapter: `kitten @ focus-tab --match`, `wezterm cli activate-pane`, Ghostty/iTerm2 AppleScript, or `wt -w 0 ft -t <index>`. The mod `$.ui.notify` is fine for notices about the session itself, because it goes through the user's `preferredNotifChannel`.

## Seven terminals fall into four tiers of control

Mapping a session to its tab is solved the same way everywhere. A SessionStart hook runs inside the agent's pane and reports `TMUX_PANE`, `KITTY_WINDOW_ID`, `WEZTERM_PANE`, `ITERM_SESSION_ID`, `TERM_SESSION_ID` or `WT_SESSION`, plus its tty, to the daemon. That hook-reported identity is the join key, which is more robust than pid-walking. Of these variables, only `WEZTERM_PANE` and `TMUX_PANE` were confirmed this session; the others come from training knowledge. Ghostty exports no per-surface id, but 1.4's AppleScript exposes each terminal's TTY and foreground PID ([Ghostty 1.4.0 notes](https://ghostty.org/docs/install/release-notes/1-4-0)). In the matrix, "TK" marks training knowledge that was not re-verified, and the rest is cited above or in the linked docs.

The tiers read straight off the table. **tmux, kitty and WezTerm** are fully drivable from a background process. **iTerm2 and Ghostty-on-macOS** are drivable after a one-time macOS Automation or API consent. Ghostty moves up from the design's "limited", because 1.4 added PID/TTY, `name override` and tab focus. **Ghostty-on-Linux and Terminal.app** can open tabs and change little else. **Windows Terminal** can launch tabs into a named window and nothing more, with no query, no close and no runtime colour. The bottom row is the reason the recommendation leans on mods. They are the one layer that behaves identically in all seven.

## Competitors share one layout, and without the diff pane crosstalk can match most of it

Every GUI competitor draws the same three things: a sidebar of agents grouped by repo with a status dot, the agent's real terminal or a chat rendering of it, and a diff or changes pane. herdr is a native app whose agents live in a local `herdr-core` server. They survive app restarts but not a reboot, and after one, "agents are not resumed". Its model is "a space for each repo and a tab for each task", with `hc run --bg` and `hc send` for orchestration ([herdr.dev](https://herdr.dev)). herdr itself admits that agents inside tmux within herdr cannot report status. Paradev is an Electron/React app with a worktree, branch and terminals per task, `.superset/config.json` setup scripts, a browser preview pane, a Changes pane and an iOS app on Pro ([GitHub superset-sh/superset](https://github.com/superset-sh/superset)). Conductor is a Mac-only Tauri app that is "chat-centric", rendering agent output itself, with a worktree per workspace and `CONDUCTOR_PORT` ([Conductor docs](https://www.conductor.build/docs/concepts/workspaces-and-branches); [Launch HN](https://news.ycombinator.com/item?id=48236770)). The sharpest first-party competitor is Claude Code's own **agent view**. It is a TUI list of background sessions (`claude agents`, `claude --bg`, `/bg`) with Needs-input states and a peek panel that can answer inline, though "for permission prompts replying doesn't answer it" ([Agent view](https://code.claude.com/docs/en/agent-view); [Claude blog](https://claude.com/blog/agent-view-in-claude-code)).

Users' complaints describe crosstalk's opening. On the Paradev launch thread they cite a "2GB" Electron app, garbled glyphs in long sessions, a login wall, Mac-only builds and $20 a month, while a visible group says "iTerm2 tabs / tmux is plenty" ([Launch HN](https://news.ycombinator.com/item?id=48236770)). With diff viewers out of scope, the competitive checklist shrinks to the elements below.

| Element | Competitor form | crosstalk, nothing-to-start version | Verdict |
|---|---|---|---|
| Sidebar of agents | herdr spaces/tabs, Paradev, Conductor | mod Pane in any session (fullscreen, ≥144 cols); band/status line elsewhere; tabs named per thread | **match**, distributed across sessions instead of one window |
| Working / blocked / done | dots, rings, chimes | hooks → daemon → mod status + tab chrome per tier | **match** |
| Agent needs you | cmux blue ring, dock badges | daemon OS notification → focus adapter; mod band in the current session | **match**, with richer text than Claude's stock "waiting for your input" ([cmux fork](https://github.com/mp-grind/cmux)) |
| Answer without switching | agent-view peek | band Buttons/Input, consumed deliveries; permission relay for sessions crosstalk starts | **better** for permission prompts |
| Launch in worktree + setup + port | Paradev, Conductor | daemon `git worktree add`, setup script, port env var, hidden tmux | **match** |
| Survive window close | herdr-core | hidden tmux server; daemon re-creates with `claude --resume` after reboot | **match, arguably better** |
| Remote machines / phone | herdr SSH, Paradev iOS | linked machines; Remote Control and phone push | **partial** |
| Browser preview pane | Paradev | OSC 8 link to the system browser | **no** |

## What the findings change in next-generation.md

The research confirms the architecture and corrects several mechanisms. **Confirmed:** the user's own sessions should stay where they are. The mod layer works inside them in every terminal, so nothing has to move. Using tmux "invisibly" for crosstalk-started sessions is sound and matches herdr-core's real benefit, since a tmux server outlives the window. A private socket (`tmux -L crosstalk -f <crosstalk.conf>`, the agent-manager pattern; [agent-manager](https://pkg.go.dev/github.com/YoanWai/agent-manager@v0.14.2)) keeps it out of the user's default server. Because crosstalk owns that config, sessions attached with `@auth open` (a new tab running `tmux -L crosstalk attach -t auth`) get crosstalk's full status line, clickable ranges and `set-titles-string` tab titles with no setup by the user. Driving the user's own tmux "through window options… rather than escape codes" is right for a second reason the design did not state. tmux drops plain OSC 9/777/99 entirely, honours passthrough only with `allow-passthrough on` ([input.c](https://github.com/tmux/tmux/blob/master/input.c); [tmux.1](https://github.com/tmux/tmux/blob/master/tmux.1)), and turns Claude Code's OSC 2 into a pane title, which ends the title war.

**Changed:** the statusline and "hook message" must become a crosstalk mod. A plugin cannot install the main `statusLine`, and classic hooks cannot reach an idle session. `@thread` answers should prefer mod widgets or a `prompt.submit` drop, with the UserPromptSubmit block as a fallback, because a blocked prompt still persists on disk. The design's own line, "crosstalk also emits herdr's open OSC 7501", should credit the Program Status Protocol, demote it to a free extra, and drop any reliance on Claude Code's own 7501 output. Claude Code emits it only after a query reply that no mainstream terminal, tmux or daemon tty write can provide. The "to test first" item about title overwrites is now known to be real, so crosstalk should rename through `sessionTitle` and never set `CLAUDE_CODE_DISABLE_TERMINAL_TITLE`. The terminal table should promote Ghostty 1.4 on macOS. It should also note that on Windows Terminal neither a tab colour nor a focus query is possible after launch, and tty writes are impossible, so Windows users get mods plus launch-time `--tabColor`. Deliveries over the inbox socket (`messagingSocketPath` in `~/.claude/sessions/<pid>.json`, which arrive in model context by default) must pass through a mod's `session.receive` so that peer text is consumed and drawn, not read by the model.

## Recommendation: build crosstalk as a mod first, chrome second, tmux third

Build three layers in priority order, all growing out of whatever session the user opened.

**Layer one is a crosstalk mod**, shipped in the existing plugin and requiring Claude Code ≥ 2.1.287. It pins a `$.ui.status` line (`◢ auth · tokens  2 people · 1 waiting`). It shows questions from other threads in an AbovePrompt band with Buttons and an Input, polled from the daemon by `$.clock.every`, so they appear even in an idle session. It consumes every peer and relay delivery in `session.receive`. It offers an opt-in Pane that lists every session, its threads and its state as the "sidebar" in fullscreen. And it hands content to the model only through deliberate `$.session.append({type:"user"})`. Classic hooks stay for state reporting: SessionStart registers the pane id, tty and `$TERM_PROGRAM`, and returns `sessionTitle`. UserPromptSubmit, PreToolUse, PermissionRequest, Notification and Stop report working, blocked and done. They also act as the full fallback when mods are off: a synchronous `systemMessage` plus a UserPromptSubmit block.

**Layer two is terminal chrome through per-terminal adapters**, never focusing on its own. Prefer APIs (kitty, WezTerm, Ghostty AppleScript, iTerm2 Python) over tty writes. Use single-syscall writes of complete sequences only for iTerm2 colour, badges and user vars. Never write queries. Post notifications from the daemon so that a click can call the focus adapter.

**Layer three is the hidden `tmux -L crosstalk` server** for sessions crosstalk starts, with an in-place switch to the user's own server when `$TMUX` is set. It extends their status format with `E:` rather than replacing it, and touches `allow-rename`/`automatic-rename` only on crosstalk's own windows. Feature-detect the tmux version (3.4 for user ranges, 3.8 for modal panes and monitor hooks). Use `claude --bg` where tmux is absent, notably native Windows, accepting that background sessions draw no mods. Started sessions may carry flags the user never types, such as development channels for permission relay. Run five spikes before committing:

| Spike | Why it decides the design |
|---|---|
| Does `sessionTitle` drive Claude Code's OSC title, and does it stick? | Picks between the cooperative and the daemon-owned title |
| Does `session.receive` see raw writes to the `messagingSocketPath` inbox? | Picks whether the daemon can keep using the socket |
| Are `$.ui.ask` answers, `prompt.submit` drops and blocked prompts ever replayed into context, including on `--resume`? | Settles the "never enters context" guarantee |
| Do `$.ui.status` and toasts render ANSI and OSC 8? | Settles colour and links in the status line |
| How reliable are tty writes beside a live Claude Code redraw, per terminal? | Settles the colour and badge fallback |

## Conclusion

The competitive question turned out to be less about terminals than about Claude Code. Once Claude Code exposed mods, "the terminal becomes the app" stopped requiring control of the terminal. It requires control of the one program the user has already started in it, and that program now offers panes, bands, status lines and a delivery interceptor that keeps other threads out of the model. Terminal chrome becomes decoration with real value (colour, a jump-to-tab click, a progress bar) that can degrade from kitty's full API to Windows Terminal's launch-only flags without breaking anything essential.

The strategic risk has also moved. herdr, Paradev and Conductor are not the threat to a nothing-to-start design. Claude Code's own agent view and supervisor are, because they already offer a first-party list of sessions with needs-input states. crosstalk's defensible ground is what those surfaces cannot do: answer a permission prompt from another session, route questions by thread across people and machines, and keep each agent's context clean. The early-access label on the mod API is the price of that ground. Pin a minimum Claude Code version and keep the classic-hook fallback alive.
